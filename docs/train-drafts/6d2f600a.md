# Make atomic capacity admission actually atomic

The concurrency reviewer should catch admission code that checks an atomic counter against a limit and increments it in a separate operation. Each operation is race-free on its own, but the invariant is not: two callers can observe the same available capacity, both pass, and then both reserve it.

Source: [cortexproject/cortex#7271](https://github.com/cortexproject/cortex/pull/7271), `pkg/storegateway/concurrent_bytes_tracker.go`.

## Examples

- Flag `if used.Load()+n > max { return err }; used.Add(n)` in an Add/Reserve/Acquire-style method.
- Also recognize a thin accessor such as `Current()` when it simply returns `used.Load()`.
- Stay quiet when one mutex covers both operations, a CAS retry loop makes the decision and update together, or code reserves first and rolls back on rejection.

## Done when

- The finding explains the compound check-then-update race and points to the capacity guard.
- Regression fixtures cover both a direct atomic load and the thin-accessor shape from the source PR.
- Clean fixtures cover mutex and CAS admission.
- `npm test`, `adversary validate .`, and `adversary pack --check .` pass.
